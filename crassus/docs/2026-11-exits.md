# Configurable profit-taking and protective exits (issue #86)

The option books in this repo close reactively: a strategy sells when its own
signal stops supporting the position. Nothing closes a position because it has
made enough money, because it has lost too much, or because the contract's
remaining premium should be salvaged before expiration. The mandatory
end-of-day flatten bounds *time*; Guideline Phelps withholds a signal-driven
exit for one window. This document describes the layer that fills the gap
between them: `crassus/exits.py`, wired into the runner between the flatten and
the account's strategy.

It is implemented, tested and **inert** until `CRASSUS_EXITS_ENABLED` is set.
The policy itself is approved: Owen approved the bounded-loss configuration on
2026-11-09 — stop `-0.50`, profit target disabled (`null`), stop bypassing the
Phelps window, profit respecting it, 15-minute re-entry cooldown — and that is
now the default in code. Activation remains a deployment setting, enabled by
Chej once this default is on the runner; the numbers are an approved starting
policy, not a calibrated optimum.

## What it does

Every cycle, for each account whose strategy is covered, the runner values each
held position against a fresh liquidation-side quote, compares that to the
position's documented average cost, and closes the most urgent triggered
position:

| Held position | Liquidation price | P&L |
| --- | --- | --- |
| Long (quantity > 0) | quote **bid** | `(bid - average_cost) / average_cost` |
| Short (quantity < 0) | quote **ask** | `(average_cost - ask) / average_cost` |

The quote must pass `Quote.is_executable` -- both sides present and no older
than the Worker's own 15-second execution cutoff, measured on the server clock.
A trigger with no usable quote does not fall through to the strategy: the cycle
returns an explicit `no_trade` naming the stuck symbols, so the strategy cannot
open a fresh position while a position that wants out has no price.

Cost basis is `client.Book`'s average cost, reconstructed each reconciliation
from the server's authoritative trade history. The Worker settles paper options
in premium terms, so the percentage is premium P&L and no contract multiplier
enters the threshold arithmetic.

## Precedence

Highest first. Implemented order in `Runner._run_account`:

1. **Session** -- `maybe_flatten` runs first and always wins. This layer never
   preempts it, duplicates it, or opens a position inside the flatten window.
2. **Protective stop** -- fires by default even inside a Guideline Phelps
   window. Phelps deliberately tolerates discomfort and has no loss bound; a
   stop whose whole purpose is bounding loss cannot be subject to it.
   `stop_bypasses_phelps: false` opts an account into strict doctrine, at the
   cost of an unbounded loss inside the window.
3. **Profit target** -- deferred by default inside a Phelps window. Taking a
   profit is not the capitulation Phelps protects against, but closing early
   also ends the convexity purchase the method paid for. Set
   `profit_bypasses_phelps: true` to let the target fire regardless.
4. **Signal reversal** -- the base strategy's own sell, with Phelps's existing
   deferral unchanged. This layer never suppresses or rewrites it.
5. **Re-entry** -- after an exit is submitted, the same contract is blocked for
   `reentry_cooldown_minutes`. The block is recorded before submission, so it
   holds even when the exit is rejected or its outcome stays ambiguous; the
   record is durable and survives a restart.

Multiple positions in one book are evaluated every cycle; one leaves per cycle
(`Decision` carries one symbol). Stops outrank profit targets, and within a
trigger class the larger absolute move leaves first.

## Defaults: the approved bounded-loss policy

Owen approved these values on 2026-11-09, and they are the code defaults. They
are an approved **starting** policy, not a calibrated optimum: the sensitivity
check over the only saved 0DTE data in the tree is summarised after the table,
and it is the reason profit-taking is disabled rather than set to the earlier
+50% placeholder.

| Setting | Default | Status and rationale |
| --- | --- | --- |
| `profit_target_pct` | `null` | **Approved: disabled.** The earlier +50% placeholder was decorative — the sample never reached it from any intraday entry (median favourable excursion −5%, p90 +16%, max +39%). Profit-taking is therefore off until a signal-anchored replay can calibrate it; the strategy's own signal decides the upside. `null` is not the same as a large number: `1.00` is an enabled +100% target that fires on a doubling, `null` can never fire. |
| `stop_loss_pct` | `-0.50` | **Approved value.** Half the debit. The sample shows the stop doing real work: hold-to-close median −76% of premium, a −50% stop median −55% and the 10th percentile lifted from −95% to −75%. |
| `reentry_cooldown_minutes` | `15` | **Operational, not statistical.** Three deployed five-minute cycles: long enough that an unchanged stale signal cannot buy the same contract straight back, short enough that a later genuine setup is not blocked. |
| `stop_bypasses_phelps` | `true` | **Approved policy.** A stop exists to bound loss; Guideline Phelps deliberately has no loss bound. |
| `profit_bypasses_phelps` | `false` | **Approved policy.** Doctrine-consistent: the window is the convexity purchase. Inert while the target is `null`, kept for any account that re-enables one. |
| `quote_max_age_s` | not configurable | The Worker's execution contract (15 s); a looser local value only produces 409s. |

### What the available data does and does not say

`sensitivity.py` (outside the repository, results in the review packet) uses the
cached QQQ 0DTE chain snapshots under
`research/synthetic_days/tests/fixtures/r2_cache/intraday` — six days, thirty
snapshots a day, about twenty-one minutes apart. It treats every regular-session
snapshot as an entry, buys the nearest-the-money contract at the quoted ask, and
walks forward at the quoted bid.

Sample: 204 entries, ATM quoted spread median 1.1%.

| Measure | Value |
| --- | --- |
| Max favourable excursion | median −5%, p75 +4%, p90 +16%, max +39% |
| Max adverse excursion | median −78%, p10 −95%, worst −99% |
| Target reachable at any point | +25% in 4%, +50% in 0% |
| Stop touched at any point | −25% in 99%, −50% in 90%, −75% in 57% |
| Hold to close | median −76%, p10 −95%, p90 −39% |
| Stop at −50% only | median −55%, p10 −75%, p90 −46% |
| Pair +50% / −50% | median −55%, p10 −75%, p90 −46% (identical: the target never fires) |

Three honest readings. The stop is the part of the policy with evidence behind
it: it truncates the left tail and improves the median by about twenty premium
points in this sample. The +50% target is beyond the observed excursion
distribution and adds nothing here; if a profit target is wanted at all, the
data points nearer +25% (which still fires in only ~4% of entries) or leaving
the upside to the strategy's own signal exit. And none of this calibrates a
level: the entries are every snapshot rather than the strategies' own signals,
the sampling is coarse, six days is not a sample, and only QQQ ATM contracts are
covered.

### The approved configuration

The approved policy is now the code default, so no account needs an `exits`
block at all; the equivalent explicit form, if an account ever needs to state
it, is:

```json
"exits": {
  "profit_target_pct": null,
  "stop_loss_pct": -0.50
}
```

`profit_target_pct: null` disables profit-taking for that account. This is the
important distinction: `1.00` would still be an *enabled* +100% target that
fires when a contract doubles, whereas `null` can never fire. With the target
disabled, the layer is purely a bounded-loss control and lets the strategy's own
signal decide the upside — which is the only half of the pair the available
evidence supports.

Why −0.50 exactly, rather than a range: in the sample, a −50% stop moves the
median outcome from −76% (hold to close) to −55% and lifts the 10th percentile
from −95% to −75%. Tighter levels fire on almost every entry (a −25% stop is
touched in 99% of entries, so it converts noise into realised losses before a
position can resolve), while −75% touches only 57% but permits a three-quarter
loss of the debit. −50% is the single value with the best evidence-to-collateral
trade in this data, and it is also the widest stop that still leaves a same-day
account solvent across a bad sequence.

The approval does not turn this into a calibrated result. Calibrating either
side still needs a signal-anchored replay, which the repository does not have
yet; a change to the stop, the disabled target, either Phelps switch or the
cooldown is a policy change, and `verify_exits.py` pins all five so it cannot
happen by accident.

## Configuration

Per account, in `accounts.example.json` (or an ignored `accounts.json`
override):

```json
{
  "alias": "Luigi",
  "username": "crassus_luigi",
  "strategy_id": "reddit_sentiment_qqq",
  "password_env": "CRASSUS_PW_LUIGI",
  "exits": {
    "profit_target_pct": null,
    "stop_loss_pct": -0.5,
    "reentry_cooldown_minutes": 15,
    "stop_bypasses_phelps": true,
    "profit_bypasses_phelps": false
  }
}
```

Unknown keys, non-numeric values, a non-positive target, a non-negative stop and
a negative cooldown are configuration errors recorded against that account
only (`runner_error`, reason `Invalid exit configuration: ...`), never a
process-wide crash and never a silent fallback.

## Activation and rollback

The layer requires `CRASSUS_EXITS_ENABLED` to be an explicit affirmative
(`1`, `true`, `yes`, `on`). Absent or anything else keeps it inert, including a
per-account `enabled: true` -- activation is a deployment decision, not a
catalog accident.

The policy below is approved and is the code default; activation is still a
separate step, and no account catalog or runtime setting was changed in the
patch that introduced the default.

1. Confirm the runner revision carries the approved default (`stop -0.50`,
   `profit_target_pct: null`, stop bypasses Phelps, profit respects it, 15-minute
   cooldown); `verify_exits.py` pins all five.
2. Set `CRASSUS_EXITS_ENABLED=1` on the Railway service and restart.
3. Verify the first cycle: a held position with no trigger produces an ordinary
   strategy decision; a triggered one produces `strategy_id: exit_policy` in the
   ledger with the full audit metadata.
4. Rollback: unset the variable (or set it to `0`) and restart. No state needs
   cleaning: `state/exits.json` only carries cooldown timestamps and is pruned
   after 24 hours.

## Durability of the cooldown record

The re-entry guard is only as good as its record of recent exits, so that record
is treated as durable state rather than a cache:

- writes go through `durability.atomic_json` (temp file, fsync, atomic replace,
  directory sync), the same path the execution intent and the ledger use, so a
  crash mid-write leaves the previous good file intact instead of a truncated
  one that would read as "no exit happened";
- a missing file is a normal first boot; a corrupt or unrecognised file is
  rebuilt from the durable evidence that already exists — the ledger's exit rows
  and any in-flight execution intent (which is fsynced before every submission,
  so no filled exit can be hiding) — and the rebuilt file is written back;
- if neither source is readable, the store marks itself untrusted, and the guard
  refuses **new entries** while leaving protective exits untouched. That is the
  deliberate asymmetry: an unknown cooldown may cost an opportunity, never a
  duplicate position.

## Audit trail

An exit decision's metadata carries `exit_trigger`, `exit_symbol`,
`exit_held_quantity`, `exit_cost_basis`, `exit_liquidation_price`, `exit_bid`,
`exit_ask`, `exit_quote_age_s`, `exit_pnl_pct`, `exit_threshold_pct` and the
resolved `exit_policy`. The ledger row records the decision, the submitted
intent's `execution_request_id`, the HTTP status, the outcome class and the
resulting account state, and the decision's `strategy_id` is `exit_policy` -- so
an exit is attributable separately from the account's assigned strategy.

## Tests

`python scripts/verify_exits.py` (51 checks) covers inclusive boundaries for
both triggers (the profit-target cases now configure an enabled target
explicitly, because the default is disabled), long and short holdings priced on
the correct side, multi-contract
books with stop-over-profit precedence, stale and missing quotes, quote errors,
the two Phelps bypasses and the unknown-entry-time case, a disabled profit
target (`null`) versus an enabled +100% one, configuration validation (including
precedence switches that must be real JSON booleans), inertness without
activation, the re-entry cooldown across a restart and its non-interference with
reducing trades, durable-state behaviour (an interrupted save keeps the previous
file and blocks new entries until a save succeeds, a corrupt file is rebuilt from
the ledger or an in-flight intent, and an unrecoverable store blocks entries
without blocking protective exits), audit-field completeness and the precedence
actually applied, and runner-level scenarios: an exit becoming a real submitted
sell attributed to `exit_policy`, a protective exit firing with no market
snapshot while new entries still wait for one, a rejected exit retried on the
next cycle with a new decision id, a settled position producing no second exit,
a pending exit intent reconciled before a new one is proposed, a live cooldown
turning the strategy's own buy into an audited `no_trade` through the runner,
and an invalid `exits` block becoming a per-account `runner_error` instead of a
trade.

## Not established here

No live or paper trade has been executed under this policy. The evidence is
unit and runner-level with fixtures; the live behaviour to watch after
activation is whether a stop and the Phelps window interact as intended on a
real 0DTE position, and whether the 15-minute cooldown ever blocks a
genuinely new setup. Those are observations for the live checks, not claims of
this branch. The threshold levels are uncalibrated by construction — see the
sensitivity section above for exactly how little the available data can say.
